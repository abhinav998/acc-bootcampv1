M01Campaign Classic in the Adobe stackv7 · v8

Campaign Classic (ACC) is Adobe's batch- and workflow-centric, cross-channel campaign management platform. It owns its own marketing database, segments it, orchestrates multi-step programs, and sends email, SMS, push, direct mail and other channels at scale.

ProductRole next to Campaign
Adobe Experience Platform / Real-Time CDPUnified profiles and audiences; audiences can be shared into Campaign
Adobe TargetOn-site personalization and testing, fed by segments Campaign produces
Adobe AnalyticsWeb behaviour; Campaign can send campaign metadata and receive re-marketing segments (v7 web analytics connectors)
Journey Optimizer (AJO)Real-time, event-triggered journeys; Campaign stays strong for batch, complex data and heavy workflow logic
AEM / AssetsContent authoring and asset storage that Campaign deliveries can reuse

Think of it as

A database + workflow engine + delivery engine, all driven by XML schemas. Almost every object you click on (a delivery, a workflow, an operator) is a row in a table described by a schema.

M10Proofs, seed addresses, test profiles and previewv7 · v8
  • Preview tab: render for a specific recipient or test profile; check both HTML and text.
  • Proof: a real send to test addresses; label [PROOF #n] added to subject. Proofs can be sent to seeds, test profiles or a substitution target.

  • Substitution addresses: send a proof with real recipients' data to a tester's inbox.

M11SMS deliveriesv7 · v8
  • Routing: an SMS external account (SMPP connector in v8/extended generic SMPP in v7) configured by admins.
  • Encoding: GSM 7-bit = 160 chars per part (153 in multi-part); UCS-2/Unicode = 70 (67 in multi-part). One emoji or Devanagari character switches the whole message to UCS-2.
  • Mobile number format: normalise to E.164 (+91…) in imports.
  • Status reports (SR) update broadLog statuses asynchronously.
  • Regulatory: in India, DLT template and header (sender ID) registration is required for commercial SMS; keep the registered template ID with the delivery.

M14Services, subscriptions, opt-out and the blocklistv7 · v8
  • Information service (nms:service): a newsletter or topic users subscribe to. Can send confirmation messages and has a validity.
  • Double opt-in: subscription sends a confirmation email; only the click confirms.
  • Opt-out link sets @blackListEmail (or unsubscribes a service, depending on configuration) via the OOTB unsubscription web app.
  • Denylist vs quarantine: denylist = the person said no; quarantine (nms:address) = the address is technically bad.
  • In FFDA, opt-out and subscription syncs are asynchronous (staging).

M17Workflow fundamentals and the work tablev7 · v8
  • Two kinds: campaign workflows (inside an operation, with delivery activities) and standalone workflows (Administration › Production › Technical workflows or your own folders).
  • Template vs instance: build a template once, create instances from it.
  • Transitions carry a population: each outbound transition points to a work table (temp:query, temp:enrich…) plus a targeting dimension and a record count.
  • Execution states: being edited, started, paused, stopped, finished; plus failed with the "Suspend on error" option.
  • Properties to set every time: execution folder, Keep interim results (off in production), log SQL queries (debug only), affinity, priority, error management (suspend / ignore), supervisors group.
Right-click a transition → Display the target to see the rows and the work table's schema. That single habit prevents most workflow bugs.

M21Scheduling, signals and workflow-to-workflow callsv7 · v8
  • Scheduler: once, daily, weekly, every N hours; with an optional validity period. Timezone set in workflow properties.
  • External signal: the receiving workflow must be started and waiting at the signal activity.
  • Trigger it from JS: xtk.workflow.PostEvent(workflowInternalName, activityName, transitionName, <variables .../>, false).
  • Passed variables arrive as vars.x in the receiving workflow.
// Parent workflow, JavaScript code activity

  "signal",                // name of the External signal activity
  "",                      // transition ("" = default)

M22Error handling, restarts and safe pausingv7 · v8
  • On most activities tick Process errors to get an Error transition; route it to an Alert and an End.
  • Workflow property In case of error: Suspend process (default) vs Ignore. Suspend keeps the evidence.
  • Restart reruns from the start; Resume continues a paused workflow; for a failed task use "Restart the task" on the activity.
  • Design for idempotency: a rerun must not double-insert (use Update data with insert or update on a business key).
  • Wrap JS in try/catch; throw after logging if you want the activity to fail visibly.
try {
  // work
} catch (e) {
  logWarning("NVB load failed: " + e);
  instance.vars.errorMsg = String(e);
  throw e;        // keep the activity in error so the Error transition fires
}

M34Schema anatomyv7 · v8
  • Source schema (xtk:srcSchema): what you write. Schema (xtk:schema): what Campaign generates from it (includes extensions, computed defaults). Edit only source schemas.
  • Root <srcSchema name namespace label labelSingular>; the main element has the same name as the schema and maps to a table.
  • <attribute> = column; <element> = sub-structure, link, or XML/memo container.
  • <key> = logical unique key (used for reconciliation and SOAP writes); <dbindex> = physical index.
  • <enumeration> declared at the schema root, used via enum="…".
  • <sysFilter> = row-level filter applied to every read (security).
  • <compute-string expr="…"/> = how a record is shown in lists and links.

M36Links: cardinality and integrityv7 · v8
<element name="recipient" type="link" target="nms:recipient"
         label="Owner" revLink="accounts" integrity="own"/>
  • A link element creates a foreign key column (e.g. iRecipientId) and, by default, a reverse collection link on the target (revLink names it).
  • 1-N: link on the "N" side (account → recipient). 1-1: add revCardinality="single". N-N: a relation table with two links.
  • revExternalJoin, externalJoin: outer joins for optional links. <join xpath-src="@x" xpath-dst="@y"/> for joins on non-key fields.
  • noDbIndex="true" skips the automatic index on the foreign key (rarely wise).
integrityAdobe's definition
defineThe source can be deleted if it is no longer referenced by a target occurrence
normal (default)Deleting the source initialises the link keys of the target
ownDeleting the source deletes the target
owncopyAs own, and duplicating the source duplicates the target
"Source" and "target" in integrity definitions are easy to misread. Always prove the behaviour on a test record: delete a test recipient and check what happened to its accounts. Design patterns for your own technical workflows

  1. Staged ingestion: land (file to work table) → validate (split good/bad) → promote (Update data into a fixed staging table, then into the business table) → archive (move file) → audit (run log row). Never write straight from a raw file into a business table.
  2. Fixed staging tables: one stable schema per feed. Date-suffixed or per-run tables break every downstream consumer (CDP, Target, reports).
  3. Idempotency: reruns produce the same result (insert or update on business keys; file names recorded in the run log and skipped if already processed).
  4. Locking: a lock option prevents overlapping runs.
  5. Error routes: every data activity has "Process errors" → Alert (with instance.vars.errorMsg) → End. Workflow property Suspend on error.
  6. Parameterisation: file patterns, table names, thresholds in options or instance.vars set in the first JS activity, so one template serves many feeds ("build once, deploy many").
  7. Guardrails: stop if input count is zero or deviates more than X% from the 7-day average.
  8. Performance: set-based activities over per-row JS; batch sizes on Update data; indexes on reconciliation keys; no interim results; schedule away from heatmap peaks and away from the cleanup window.
  9. Runbook: purpose, schedule, inputs/outputs, owners, alert recipients, rerun steps, known failure modes.

M57Security: operators, rights and zonesv7 · v8

Answer key: problems to find
  • Unitary writes in a loop (FFDA: blast calls not recommended, very slow).
  • Date-suffixed table per run (breaks downstream consumers, no stable schema, clutters DB).
  • SQL code relying on local DB syntax/indexes against Snowflake data.
  • Integer keys/sequences assumed; FFDA uses UUIDs and doesn't enforce unicity.
  • No awareness of staging latency (hourly sync) before campaigns use the data.
